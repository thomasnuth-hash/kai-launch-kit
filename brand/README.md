# Kai design language

Two generated files. Both are data, both are readable by a person, a script or
a model, and neither is hand-maintained.

| File | What it is | Regenerated by |
|---|---|---|
| `design-language.json` | Themes, washes, ramps, formats, motifs, icons, announcement categories, presets. The look. | `python3 tools/design_language.py extract` |
| `tile-schema.json` | Every field of a tile: kind, allowed values, default. The contract. | open `tile-maker/schema.html` |
| `tokens.css` | The subset the video cuts use. | hand-written |
| `brand-notes.md` | Palette, type, motifs, and what is confirmed vs approximated. | hand-written |

## Why they are separate

`design-language.json` says what Kai looks like. `tile-schema.json` says what
you are allowed to ask for. You need both to produce a valid tile without
opening the UI: the schema tells you the fields and their legal values, the
design language tells you what those values mean.

## Making a tile without the UI

Every field in `tile-schema.json` maps to a control of the same `id` in the
tool. Take the defaults, change what you need, and check each value against
its `options` where the control is an `enum`.

```json
{
  "type": "stat",
  "format": "1200x1200",
  "eyebrow": "Report",
  "to": "92",
  "suffix": "%",
  "head": "of assets have an accountable owner",
  "source": "Kai 2026 State of Autonomous Defense Report",
  "wash": "default",
  "motif": "weave"
}
```

Anything category-dependent carries a `note` saying so — `imgTreat` is the
only one today, and its legal values differ between launch and event.

## Changing the look

Edit `design-language.json`, then:

```bash
python3 tools/design_language.py inject     # write it into the tool
open http://localhost:4340/tile-maker/rendertest.html   # 1054/1054 expected
```

The tool stays a single self-contained file, so it still runs offline and can
be handed to anyone outside Kai. It just isn't where the design is authored.

## What is not yet wired

These files were lifted out of the tool, which means they match what the tool
already did — not necessarily what Figma says today. Pointing this at the real
library needs a Figma **file** URL (`figma.com/design/…`); a folder link has no
file key and the API cannot read it. With one, `design-language.json` can be
generated from Figma variables and styles instead of from the tool, and the
round-trip check becomes a drift alarm between design and code.

## What Figma actually has — checked 29 Sep 2026

File: `Marketing-Site`, key `vW8VWvTF2KkMx7mZeafuCZ`. Three libraries are
subscribed: **Library | Product**, **Library | Brand**, **Library | Presentation**.

| Looked for | Result |
|---|---|
| Colour variables | none — searched `brand`, `colour`, `blue`, scoped and unscoped |
| Text styles | none |
| Gradient styles | none |
| Components | found, in Library \| Product (Button, FAB, Kai Magic Label, …) |

Search works — components come back. Variables and styles do not, because
**there are none published**. The brand colours in Figma are raw fills, so
there is no token layer to sync from. That is why the tile maker's values were
typed in by hand, and why its spec still has `{{FIGMA_FILE_URL}}` unfilled.

So the direction is currently the other way round: `design-language.json` is
the closest thing to a machine-readable Kai design language that exists. To
make Figma the source instead, someone has to publish variables there — colour
and type as named variables in Library | Brand. Once they exist,
`tools/design_language.py` gains a `pull` mode and the round-trip check
becomes a drift alarm.
